# ChatGPT Web 适配

目标是让扩展、网关和 Drafts 在用户选择的模型上正常发送、等待、恢复和展示完整答案。
用户曾反复强调：修复异常请求的实际原因，比增加“正在思考”的诊断更重要；
源码通过测试也不能代替运行中的版本验证。

这是项目维护 skill，放在 `.agents/skills/`，不是扩展 `Agents -> Skills` 中的运行时技能。
从仓库根目录运行项目命令，遵循当前 `AGENTS.md` 与 `package.json`。

## 先确定变化和故障所在层

1. 读报错原文、正在加载的官网资源和已安装扩展目录。区分文件拆分/改名、模块职责迁移、
   请求语义变化、流解析问题、缓存问题、旧进程或旧脚本仍在运行。
2. 对照同一登录环境下官网正常请求与扩展请求，以及当前公开 JS 的实际调用关系。
   已获电脑操作授权时可直接观察页面；历史会话与抓包只作为证据，不作为新的操作授权。
3. 查本项目已有实现和回归案例。按需读 [试错记录](references/lessons.md)，
   定位改动和部署时读 [验证与代码入口](references/validation.md)。
4. 先说明具体缺口再修复。旧快照中的混淆名、默认模型和字段名都不是未来版本的常量。
   替换 `resources/` 的参考 JS 不会自动修复发送客户端。

请求链路：聊天页 → 后台 provider → 专用 ChatGPT 代理页 → 官网 conversation HTTP API。
网关请求由 `scripts/api-server.mjs` 经扩展 API Server 桥接页进入同一链路。
改变任何一层的字段时，检查创建、续聊和恢复读取的传递是否一致。

## 必须保留的行为

- **正式发送一次。** 已提交或是否提交不确定时，恢复已有轮次；不要重放 conversation
  写请求。HTTP resume 虽用 POST，却读取已有回答，和重新发送用户问题不同。
  超时、断流、解析失败都不能证明尚未发送。
- **校验使用当前页面的原生实现。** 保留同一 MAIN 文档的身份校验和现有桥接边界，
  新版原生网络路径的凭据留在 MAIN。旧版分支仍按其已验证契约处理。
  不复制抓包令牌、不吞校验失败、不伪造成功状态或输入/遥测。
  注入函数必须闭包自包含，检查最终生产包的序列化结果。
- **兼容按行为确认。** 已知映射与未知版本能力识别都要核对请求、身份、校验和网络函数的
  真实职责；函数存在和参数个数相近不够。保留 `expectedIdentity`、取消和 `retry: never`。
  发现 fetch 包装时沿调用关系核实是否只发送一次，不为通过识别而放松未知实现的检查。
- **模型默认集中管理。** 读取账号可用目录，区分 Chat / Work、Thinking / Pro / Auto。
  用户配置、官网 wire 参数与响应中的实际模型分别核实。网关和 Drafts 默认委托扩展；
  保留用户显式覆盖，续聊遵循会话模型，避免新增另一处硬编码默认值。
- **流结束与答案完成分别判断。** 解码首流与 resume，保留断线时的 delta 状态和 offset。
  `[DONE]` 或 `message_stream_complete` 不是所有分片都可展示的证明；
  `finished_successfully` 配合 `end_turn: false` 仍可能只是片段。
  隐藏分片不覆盖可见合并答案，续聊父消息采用服务端实际 continuation 标识。
- **输出适配覆盖所有消费者。** 同时检查实时流、历史 GET、扩展渲染和 Drafts transcript。
  GenUI 只静态解释支持的组件，转为可移植 HTML；不执行生成代码、hooks 或处理器。
  保留已解析且在 safe URL 集合中的引用，不支持的构造使用官网 Markdown 回退。
- **Drafts 等待状态必须匹配具体轮次。** Get 保留未发文本、发送标识和原请求参数；
  有 `pendingMessageId` 时优先精确匹配，不能用同文旧问题的答案解除等待。
  `pending: false` 单独不足以表示刚发的轮次已完成。
  仅在明确 `dispatched: false` 时释放发送标识；结果不确定时保留并先读取会话。

## 验证实际行为

复现已观察到的缺口，使用人工构造且不含账号信息的回归样本。流问题经过真正 SSE
读取器分块回放，不只直接调用解码器；部署影响 MAIN 注入时也验证生产构建。
检查用户输入没有被输入法截断，中文通过粘贴后读取输入框确认再发送。

需要验证思考、工具或可视化时，用用户指定的自然长任务。项目用户明确拒绝
“测试是否适配”“Reply OK”等机器式短问题；这类回复无法验证实际工作过程。
可视化任务例子为 `整理一下最近5天的值得关注的新闻。可视化`。这是合适的测试形状，
不是每次维护都自动发送的任务。准备和只读检查完成后，在当前授权范围内发送一次。

等待真实完成，按需只读检查进度、resume 或 GET。分钟级任务可能超出预期的 2–5 分钟，
不要因此重发。记录请求及响应的模型/强度、服务端思考或工作耗时、终态、答案尾部、
引用与布局；总耗时和服务端思考时长分别报告。缺少中间思考事件不是未思考的定论，
一次成功也不能保证服务端未来不会限流或改变处理。

## 更新与交付

改到发送/读取/输出的契约时，检查 Drafts Action 2 和 Action 3 是否需要成对更新。
构建并核实安装目录，重新加载扩展，刷新代理页与桥接页；改了网关脚本则重启已有进程，
保留用户端口和认证配置。不要把 `build/` 成功视为已安装、重载或重新连接成功。
只更新被修改的部署层；本次只写 skill 或文档时不重新构建、不发送测试消息。

允许进 Git 的内容是维护原则、公开版本事实、代码和合成测试。
原始会话、账号关联 UUID、私人目录、HAR/SSE 捕获、凭据和运行日志留在仓库外；
标记 sanitized 的文件也要当作可能含秘密。需要引用历史时提炼结论，链接仓库维护文档。

交付时说明官网具体变了什么、修复后的行为、测试证据和观测边界，并分别报告：
源码、构建、安装/重载、网关进程/桥接、Drafts 已安装副本的状态。
仓库脚本更新不等于用户 Drafts 副本已更新；替换时保留 `BASE_URL` 和 `API_TOKEN`。
后续遇到新事实，补充带日期的案例并修订被推翻的原则，不把所有历史版本硬编码进入口。
