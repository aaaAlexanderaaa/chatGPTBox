# Repair documentation discipline

## Outcome and authority

The user requested learning from `template-project` and directly optimizing this
project's documentation because its existing discipline was harming quality.
The intended result is a usable current reading path, durable ownership and
lifecycle rules, and truthful verification claims. This authorizes the bounded
documentation repair and supporting structural checks, not product changes.

## Baseline and gap

The initial worktree was clean. The local agent entrypoint was ignored by Git,
described retired settings/runtime features, and named a removed test command.
Product files, completed work, old roadmaps, and dated protocol reports lacked
machine-readable lifecycle. A future worker could follow old plans as current
authority. Root contribution entrypoints disagreed. Documentation-only changes
were outside PR checks.

## Complete end state

- Current decisions are reachable from the documentation map and concise root
  entrypoints; structure has its own verified source map.
- Product direction and remaining target designs are distinguishable. Old
  source text remains available with clear limits.
- Shared document and delivery rules have one owner each. Metadata and links
  have a small dependency-free check with tested failure cases and a PR job.
- This plan and its evidence finish with actual results and limits.

## Execution and recovery

1. Compare the reference's ownership, lifecycle, attribution, and delivery rules
   with this repository and its code/workflows.
2. Establish the local documentation/development owners and architecture map.
3. Reconcile product entrypoints, retain historical originals, classify old
   records, and align contributor and agent routes.
4. Implement the bounded checker, positive and negative fixtures, package
   commands, and documentation PR job.
5. Exercise current reader routes, inspect the diff for lost decisions, run
   affected checks, and close this plan with linked evidence.

Preserve original product records before rewriting their entrypoints. Keep
historical paths stable. Do not promote old test counts into current evidence,
revoke accepted account boundaries, or claim full engine acceptance. A mistake
in classification is corrected from the preserved original and source code;
this change performs no product-data migration.

## Verification and completion

Acceptance covers owner discovery, lifecycle separation, preservation of live
decisions and historical sources, checker rejection of sibling defect cases,
and documentation-only PR coverage. Completed on 2026-10-23:

- The map, architecture, documentation/development owners, product entrypoints,
  contributor routes and commit-ready agent entrypoint are reconciled.
- Two original product bodies and 17 existing record bodies were checked against

- The checker reports 44 files, no errors, and four pre-existing historical
  reference advisories. Its 22 positive/negative fixtures, lint, focused

- Current reader routes were reviewed in this context. Live-service acceptance,
