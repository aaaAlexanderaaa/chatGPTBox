# 浏览器助手的产品承诺与心智模型

状态：产品方向已通过。确认日期：2026 年 10 月 21 日。配置格式与实现细节仍需由实际使用推导。

**ChatGPTBox 让你在浏览、阅读和写作的地方，直接用自己选择的 AI 帮你做事；好用的做法能够留下来，按你的需要继续改变。**

用户需要先获得实际帮助。自定义、接口与编排让这种帮助适合自己的工作方式，并随着 AI 和工具能力发展而增长。它们应当降低反复搬运内容、解释要求和维护配置的负担。

## 要改变的使用体验

用户已经在浏览器里看到文章、讨论、视频、图片或输入框，也可能已经有偏好的 AI。使用 AI 时，常要自行判断取哪些内容、搬到哪里、怎样提问，以及怎样把回答用回正在做的事情。遇到新的做法，又需要重复这套工作。

ChatGPTBox 应承担浏览器与 AI 之间这部分衔接：让用户方便地指出处理对象，调用合适且由用户选择的能力，让结果直接服务于当前工作，并保留值得复用的做法。

价值体现在具体所得：读文章时理解关键内容和依据；写作时得到能直接修改的文字；查证时对照来源；委派操作时知道事情进行到了哪里。更多按钮、更多接口、更多配置字段，只有改善这些结果才有价值。

## 用户只需形成一个稳定的理解

> 我在这里让 AI 帮我做一件事。做法顺手，就留下来，下次直接用。

“这里”来自用户正在看的内容、选中的部分、输入位置或明确指定的材料。“做一件事”可以是解释一句话，也可以是跨网站持续推进一个任务；使用者不必先把要求翻译成组件和执行协议。

调用入口可以是常用功能，也可以是直接提出要求。两种方式共享当前工作的上下文，用户不必为获得预置功能重新说一遍，也不必为一个新要求先创建配置。

这里的“功能”就是保存下来的一种做法：处理什么、希望怎样处理、使用哪些能力，以及结果怎样使用。用户可以从预置开始、修改现有功能、导入别人的做法，或把一次满意的使用保存下来。不存在必须先对话、再保存、再配置的固定学习流程。

## 产品承诺怎样兑现

### 在当前工作中得到帮助

选文提问应当直接得到解答；要求标出值得关注的地方，应当能在原文看到标注与理由；改写输入，应当能比较并使用改写结果。一次调用不必先经过功能库或配置编辑器。

不同工作可以有适合自己的呈现。对话便于追问，原文标注便于阅读，差异便于改写，任务进度便于跟踪操作。共同的使用理解不要求所有结果都进入同一种聊天卡片。

### 清楚自己交给 AI 的是什么

发送网页链接、读取当前正文和处理选文，是不同的做法。用户应能分辨和改变它们，不需要理解抽取器或资源注册表。仅发送链接的功能保留这种语义；连接不能读取原文时说明实际情况，不偷偷换成上传正文。

站点适配的价值，是让文章、评论、字幕、代码差异等内容取得准确、使用自然。网站差异由扩展尽量处理，用户只需理解与本次任务有关的内容范围。

### 能按自己的要求改变做法

“总结”可以改成“找出我还不知道的观点”；“高亮”可以改成“标出论证薄弱的原文并解释”。用户可以告诉 AI 怎样修改，也可以直接编辑配置。产品负责把修改落实成可理解、可试用的行为。

预置应当是已经用实际内容打磨过的做法。它们减少开始使用的负担，同时保留修改、复制、组合与分享的空间。同一组功能可以使用不同 AI，也可以调用一套完整的外部能力。

### 所选能力能做到多少，就如实提供多少

API 可能具备图像理解、搜索和工具调用；agent 可能自行推进任务；持续工作的 agent 还可能跨中断继续执行。这些差异影响实际能力，不能按厂商名或传输方式推断。

日常操作不要求用户先选择 L1、L2、L3。相关差异在需要作决定时出现，例如是否能读取链接、是否操作当前浏览器、关闭窗口后任务是否继续。无法满足时说明缺少什么，并提供可行的调整方式。

## 从一次使用到自己的助手

第一次打开一篇文章，用户可以直接用一个好的“速览”预置，也可以提出新的要求。得到结果后，他说“结合我关注的方向，标出值得读的原文，告诉我原因”。这次要求可以只影响本次，也可以保存为以后使用的功能。

以后这个功能可以换模型、加入自己的资料、结合搜索，或把一部分工作交给外部 agent。增长的是同一做法能够完成的工作；普通阅读依然直接可用。兴趣记录是可选材料，是否读取和更新由用户决定。

这个例子说明使用与定制如何衔接，不规定所有功能的形态。图片提问可以直接发起，文件转换可以直接调用成熟工具，浏览器 agent 可以接手完整任务。它们都应让使用者知道正在做什么、得到什么、怎样调整。

## 选择的产品重心与代价

以配置和功能库为主入口，便于集中管理复杂自动化，但会让日常使用首先面对“怎样组装助手”。以当前工作为主入口，能够先提供帮助，同时需要扩展处理上下文、自然呈现和修改复用之间的衔接。

**已确认选择后者：主入口留在用户正在工作的网页，配置库承担管理与扩展。** 这允许保留完整的配置能力，也要求我们承担更好的预置、站点适配和原生交互设计。不能用“让 AI 生成配置”替代这些产品工作。

因此，通用配置编辑器和工作流画布暂不作为产品中心。需要精细装配时，它们仍可成为工具。字段数、协议层数和编排形式应由真实组合需求验证，当前不据此固定整体架构。

如果实际使用表明用户主要在集中搭建和运行跨网站自动化，而很少在当前内容中获得即时帮助，就需要重新评估这个重心。支持用户自己构建 agent 的方向保留，不要求所有使用者先成为 agent 构建者。

## 扩展应承担哪些工作

ChatGPTBox 主要承担网页与 AI 之间的衔接、适合浏览器的结果交互，以及做法的保存与修改。连接的 AI 和工具承担其真实具备的理解、规划与执行能力。

Browser Use、MarkItDown 和既有知识库，可以按实际接口完整接入，不必拆成扩展预先规定的业务动作。确实需要由扩展补充的浏览器接口保持开放，组合形式可以由用户和 AI 决定。

通用 agent 运行时、长期记忆系统和统一编排平台，不因“未来可能需要”就成为前置建设。用户在浏览器里构建 agent 时，可以选择相应执行能力；每一项新增机制应说明它改善了哪种实际使用。

## 翻译范围与后续参考

翻译专项建设暂不纳入近期范围，包括新增翻译引擎、整页双语呈现与专用翻译集成。已有翻译提示词继续沿用通用功能机制。未来接入成熟能力的空间保留，不为潜在方案提前建设专用框架。

用户指定 Kiss Translator、Read Frog 作为后续翻译能力参考，Page Assist、ChatHub 作为同类开源产品参考。需要相应能力时，优先考察现有项目的经验和可复用实现，再判断需要补充什么；具体依赖和接入方式尚未选定。

## 怎样判断这个方向是否成立

产品验证首先观察使用者能否做到以下事情：

- 不理解配置结构，也能把眼前的内容交给自己选择的 AI，得到适合当前工作的帮助。
- 能说清本次交出的是链接、选文、正文或其他材料，且实际处理范围与理解一致。
- 对一种用法提出修改后，实际结果随之改变；再次使用时无需重新解释同一要求。
- 新要求能通过改变做法或接入已有能力实现，不总要等待扩展新增一种业务按钮。
- 简单使用保持直接，复杂任务保留足够的控制、依据与进度，用户知道结果是否可以采用。

下一轮验证采用真实页面和真实使用要求，重点检查从理解、调用到使用结果的完整过程。JSON 合法、按钮能点、原型排版正常，只能证明各自的局部性质。

## 本轮修正与后续设计的依据

用户已确认本设计的产品承诺、心智模型与“以当前工作为主入口”的重心，并明确暂缓翻译专项建设、保留未来接入视野、参考成熟开源实现以减少重复建设。此确认不将工程候选中的字段、执行器或设置布局直接升级为定稿。

上一轮首先定义了配方、资源、执行器、输出与配置 UI。它们保留在[工程候选方案](../history/2026-10-21-browser-assistant-engineering-exploration.md)中，供需要时检验；配置样例与交互原型不再承担产品定稿依据。后续工程设计应由这里要兑现的使用结果推导，并允许删改原有抽象。
