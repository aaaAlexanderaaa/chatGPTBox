# 浏览器助手的产品承诺与心智模型

状态：产品方向已通过。确认日期：2026 年 10 月 21 日。配置格式与实现细节仍需由实际使用推导。

2026-10-30 的[官网输入增强目标](#experience-design-2026-10-30)记录在本文末尾。
用户已同意首批实施范围；实现进度见[交付计划](../plans/2026-10-30-chatgpt-native-input.md)。
后续候选与隐私保证的验收仍各自区分，不能由批准实施推定已经实现。

**ChatGPTBox 让你在浏览、阅读和写作的地方，直接用自己选择的 AI 帮你做事；好用的做法能够留下来，按你的需要继续改变。**

用户需要先获得实际帮助。自定义、接口与编排让这种帮助适合自己的工作方式，并随着 AI 和工具能力发展而增长。它们应当降低反复搬运内容、解释要求和维护配置的负担。

## 要改变的使用体验

用户已经在浏览器里看到文章、讨论、视频、图片或输入框，也可能已经有偏好的 AI。使用 AI 时，常要自行判断取哪些内容、搬到哪里、怎样提问，以及怎样把回答用回正在做的事情。遇到新的做法，又需要重复这套工作。

ChatGPTBox 应承担浏览器与 AI 之间这部分衔接：让用户方便地指出处理对象，调用合适且由用户选择的能力，让结果直接服务于当前工作，并保留值得复用的做法。

价值体现在具体所得：读文章时理解关键内容和依据；写作时得到能直接修改的文字；查证时对照来源；委派操作时知道事情进行到了哪里。更多按钮、更多接口、更多配置字段，只有改善这些结果才有价值。

## 用户只需形成一个稳定的理解

> 我在这里让 AI 帮我做一件事。做法顺手，就留下来，下次直接用。

“这里”来自用户正在看的内容、选中的部分、输入位置或明确指定的材料。“做一件事”可以是解释一句话，也可以是跨网站持续推进一个任务；使用者不必先把要求翻译成组件和执行协议。

调用入口可以是常用功能，也可以是直接提出要求。两种方式共享当前工作的上下文，用户不必为获得预置功能重新说一遍，也不必为一个新要求先创建配置。

这里的“功能”就是保存下来的一种做法：处理什么、希望怎样处理、使用哪些能力，以及结果怎样使用。用户可以从预置开始、修改现有功能、导入别人的做法，或把一次满意的使用保存下来。不存在必须先对话、再保存、再配置的固定学习流程。

## 产品承诺怎样兑现

### 在当前工作中得到帮助

选文提问应当直接得到解答；要求标出值得关注的地方，应当能在原文看到标注与理由；改写输入，应当能比较并使用改写结果。一次调用不必先经过功能库或配置编辑器。

不同工作可以有适合自己的呈现。对话便于追问，原文标注便于阅读，差异便于改写，任务进度便于跟踪操作。共同的使用理解不要求所有结果都进入同一种聊天卡片。

### 清楚自己交给 AI 的是什么

发送网页链接、读取当前正文和处理选文，是不同的做法。用户应能分辨和改变它们，不需要理解抽取器或资源注册表。仅发送链接的功能保留这种语义；连接不能读取原文时说明实际情况，不偷偷换成上传正文。

站点适配的价值，是让文章、评论、字幕、代码差异等内容取得准确、使用自然。网站差异由扩展尽量处理，用户只需理解与本次任务有关的内容范围。

### 能按自己的要求改变做法

“总结”可以改成“找出我还不知道的观点”；“高亮”可以改成“标出论证薄弱的原文并解释”。用户可以告诉 AI 怎样修改，也可以直接编辑配置。产品负责把修改落实成可理解、可试用的行为。

预置应当是已经用实际内容打磨过的做法。它们减少开始使用的负担，同时保留修改、复制、组合与分享的空间。同一组功能可以使用不同 AI，也可以调用一套完整的外部能力。

### 所选能力能做到多少，就如实提供多少

API 可能具备图像理解、搜索和工具调用；agent 可能自行推进任务；持续工作的 agent 还可能跨中断继续执行。这些差异影响实际能力，不能按厂商名或传输方式推断。

日常操作不要求用户先选择 L1、L2、L3。相关差异在需要作决定时出现，例如是否能读取链接、是否操作当前浏览器、关闭窗口后任务是否继续。无法满足时说明缺少什么，并提供可行的调整方式。

## 从一次使用到自己的助手

第一次打开一篇文章，用户可以直接用一个好的“速览”预置，也可以提出新的要求。得到结果后，他说“结合我关注的方向，标出值得读的原文，告诉我原因”。这次要求可以只影响本次，也可以保存为以后使用的功能。

以后这个功能可以换模型、加入自己的资料、结合搜索，或把一部分工作交给外部 agent。增长的是同一做法能够完成的工作；普通阅读依然直接可用。兴趣记录是可选材料，是否读取和更新由用户决定。

这个例子说明使用与定制如何衔接，不规定所有功能的形态。图片提问可以直接发起，文件转换可以直接调用成熟工具，浏览器 agent 可以接手完整任务。它们都应让使用者知道正在做什么、得到什么、怎样调整。

## 选择的产品重心与代价

以配置和功能库为主入口，便于集中管理复杂自动化，但会让日常使用首先面对“怎样组装助手”。以当前工作为主入口，能够先提供帮助，同时需要扩展处理上下文、自然呈现和修改复用之间的衔接。

**已确认选择后者：主入口留在用户正在工作的网页，配置库承担管理与扩展。** 这允许保留完整的配置能力，也要求我们承担更好的预置、站点适配和原生交互设计。不能用“让 AI 生成配置”替代这些产品工作。

因此，通用配置编辑器和工作流画布暂不作为产品中心。需要精细装配时，它们仍可成为工具。字段数、协议层数和编排形式应由真实组合需求验证，当前不据此固定整体架构。

如果实际使用表明用户主要在集中搭建和运行跨网站自动化，而很少在当前内容中获得即时帮助，就需要重新评估这个重心。支持用户自己构建 agent 的方向保留，不要求所有使用者先成为 agent 构建者。

## 扩展应承担哪些工作

ChatGPTBox 主要承担网页与 AI 之间的衔接、适合浏览器的结果交互，以及做法的保存与修改。连接的 AI 和工具承担其真实具备的理解、规划与执行能力。

Browser Use、MarkItDown 和既有知识库，可以按实际接口完整接入，不必拆成扩展预先规定的业务动作。确实需要由扩展补充的浏览器接口保持开放，组合形式可以由用户和 AI 决定。

通用 agent 运行时、长期记忆系统和统一编排平台，不因“未来可能需要”就成为前置建设。用户在浏览器里构建 agent 时，可以选择相应执行能力；每一项新增机制应说明它改善了哪种实际使用。

## 翻译范围与后续参考

翻译专项建设暂不纳入近期范围，包括新增翻译引擎、整页双语呈现与专用翻译集成。已有翻译提示词继续沿用通用功能机制。未来接入成熟能力的空间保留，不为潜在方案提前建设专用框架。

用户指定 Kiss Translator、Read Frog 作为后续翻译能力参考，Page Assist、ChatHub 作为同类开源产品参考。需要相应能力时，优先考察现有项目的经验和可复用实现，再判断需要补充什么；具体依赖和接入方式尚未选定。

## 怎样判断这个方向是否成立

产品验证首先观察使用者能否做到以下事情：

- 不理解配置结构，也能把眼前的内容交给自己选择的 AI，得到适合当前工作的帮助。
- 能说清本次交出的是链接、选文、正文或其他材料，且实际处理范围与理解一致。
- 对一种用法提出修改后，实际结果随之改变；再次使用时无需重新解释同一要求。
- 新要求能通过改变做法或接入已有能力实现，不总要等待扩展新增一种业务按钮。
- 简单使用保持直接，复杂任务保留足够的控制、依据与进度，用户知道结果是否可以采用。

下一轮验证采用真实页面和真实使用要求，重点检查从理解、调用到使用结果的完整过程。JSON 合法、按钮能点、原型排版正常，只能证明各自的局部性质。

## 2026-11-04 功能编辑与助手唤出修正

来源是本次用户反馈：“编辑要到页面顶部、开了模板的时候输入就失效了，UI不好看”。
以下是针对现有界面的实施判断，不代表用户逐项指定了布局。采用参考项目的
交互方法：保留反馈原意，明确状态、焦点、尺寸和下一步，并观察实际运行结果。

功能库继续服务于管理做法。名称、处理材料、结果和启用状态应便于浏览；支持搜索。
编辑在所选功能的位置展开，焦点进入名称，保存或取消后回到原操作位置。
新建和复制有明确的编辑标题；错误留在编辑区并保留草稿。入口分配、连接和模板
细节按需展开，避免每条功能都占据完整配置表单。禁用功能仍可搜索、编辑和启用。
导入文件读取和配置保存期间，功能库暂时停用编辑控件，防止并发写入旧配置。
保存成功后才更新已保存状态；失败后恢复操作并保留草稿，供修正或重试。

模板开关改变变量展开方式，不应使当前选文或输入框材料消失。模板没有引用
`{{selection}}` / `{{content}}`（含既有别名）时，仍在请求中附上所选材料；
引用这两类变量时，它们都指向本次选择的材料。编辑器给出用法说明和变量插入入口，
切换开关保留指令文本与中文输入。保存失败可重试，不丢失草稿。

助手仍在当前网页中使用。优先展示可运行的功能、处理要求和运行按钮；不可用功能
说明缺少选文或输入框。材料范围、结果形式和连接可检查、更改，运行前保留材料预览。
开启助手不发送请求；仅已有明确自动运行入口和主动运行可以调用 AI。
助手是非模态对话框：打开进入指令，内部 Escape 关闭并返回原焦点，中文组词时
Escape 不关闭。高度由视口限制，内容区滚动，运行入口保持可达。

保留项目现有字体、主题和语义颜色；功能库使用现有 UI 组件与设置布局，助手样式由
`src/browser-assistant/styles.css` 拥有。窄容器中的操作换行，字段在必要时单列；
验证覆盖窄、中、宽容器、明暗主题、键盘焦点、搜索无结果、保存失败和模板提交。
本轮是局部交互修正，不改变功能格式、引擎优先级或结果应用的确认边界。
[本轮验证记录](../evidence/2026-11-04-history-backup-and-functions.md)区分受控
交互、合成资源检查、真实用户环境和安装状态。

## 本轮修正与后续设计的依据

用户已确认本设计的产品承诺、心智模型与“以当前工作为主入口”的重心，并明确暂缓翻译专项建设、保留未来接入视野、参考成熟开源实现以减少重复建设。此确认不将工程候选中的字段、执行器或设置布局直接升级为定稿。

上一轮首先定义了配方、资源、执行器、输出与配置 UI。它们保留在[工程候选方案](../history/2026-10-21-browser-assistant-engineering-exploration.md)中，供需要时检验；配置样例与交互原型不再承担产品定稿依据。后续工程设计应由这里要兑现的使用结果推导，并允许删改原有抽象。

## 2026-10-30 官网输入增强：现状、目标与首批交付

**在保留现有网页助手的基础上，增加可以独立开启的 ChatGPT 官网增强。
首批新增两件事：普通粘贴触发本地脱敏，以及在官网输入框旁调用已有改写功能。**
用户仍在 ChatGPT 官网输入、发送和阅读回答，不必为了这两件事搬进 Box 对话窗口。

用户在 2026-10-30 明确回复“同意，开始”，授权实施本节的首批范围；代码和生产构建已加入两条链路，
受控浏览器流程已验证，真实官网与安装验收仍单独记录。本节回应用户关于官网体验、安全粘贴、简单写作、
外部工具覆盖和轻重缓急的要求；最后一次修正补上了此前未说清的现状与交付终点。
[审查与证据](../evidence/2026-10-30-browser-experience-review.md)记录事实及取舍，
[架构](../../ARCHITECTURE.md#browser-experience-proposal)拥有依赖与数据边界。

### 实施前的基线与本次变化

实施前 ChatGPTBox 已经有网页阅读、写作、功能保存和多种 AI 连接，并非要从零建设。
但“能用 ChatGPT Web 作为引擎”与“改善用户直接使用 ChatGPT 官网”是两件事。
当前官网相关代码主要服务于连接、代理请求、历史和恢复；不能据此推定已覆盖
官网用户自己的粘贴、发送和每条消息。

下表记录实施前基线，新增行为的当前步骤见[使用指南](../browser-assistant.md#chatgpt-官网输入增强)。

| 用户正在做的事 | 实施前已经实现 | 已接受的目标与范围 |
| --- | --- | --- |
| 在普通网页阅读 | 选文/正文/链接范围、提问、原文标注与定位、保存功能 | 保留并复用；本轮不另建阅读系统 |
| 在网页输入框改写 | 通用功能入口；原文与建议并列预览；确认后整体替换；一次撤销与过期检查 | 复用这条路径；首批为 ChatGPT 原生输入框增加定向入口和编辑器适配，不另建写作引擎 |
| 向 ChatGPT 官网粘贴材料 | 没有原生粘贴自动脱敏能力；通用 AI 功能也不是本地隐私检查 | **首批新增：普通粘贴先在本机检查，命中后自动生成脱敏候选，确认后再插入** |
| 直接阅读官网回答 | 现有请求诊断记录针对扩展发出的请求，不能覆盖全部原生消息 | 后续单独考虑原生消息的实际模型、耗时与思考信息；不放进首批 |
| 从桌面软件或外部客户端使用 AI | 现有 API/MCP、网页引擎与其他连接 | 沿用现有接口；官网原生聊天与本地粘贴检查不经过 gateway |

首批完成后，用户能明确得到两个变化：粘贴敏感材料时不必先手动搬到另一个
脱敏工具；修改当前草稿时不必重新寻找通用功能入口。已有阅读、写作与连接
能力仍是共享底座，不因新增官网增强而复制一套。

### 首批使用一：普通粘贴时自动检查并生成脱敏文本

以下为已接受的操作契约，示例使用虚构文本。实现与真实官网验证分别见交付记录。

1. 用户在 `Sites` 中打开 ChatGPT 的“本地粘贴检查”。设置说明支持的浏览器、编辑器、
   检测项目及未覆盖的输入方式；默认关闭，不接管全局剪贴板。
2. 用户照常在 ChatGPT 主对话输入框按 `Ctrl/Cmd+V` 或使用支持的粘贴菜单。
   扩展暂缓这次纯文本插入，在本机检查，不调用远端 AI。
3. 完整检查且没有命中时，按原选区插入文本。命中时自动生成脱敏候选，
   页面仅显示待确认状态；原文与候选的比较放在独立的扩展审查窗口。
4. 例如 `请联系 demo@example.com，客户名为示例甲公司`，在邮箱规则和用户自定义
   `示例[甲乙]公司 → [客户]` 条目命中后，候选为
   `请联系 [EMAIL_本次标识_1]，客户名为 [客户]`。
   用户可以调整命中项，再选择“插入所选结果”或取消。
5. 只有仍然有效的目标输入框才能接收结果。用户随后照常点击官网发送；
   本功能不会代发消息。检查失败或未完成时不自动贴入原文。

“自动”指普通粘贴就启动检查和替换生成；首批对命中结果保留确认。
另开窗口手动粘贴可以作为替代路径，但**只做出手工审查窗口，不能算完成了
普通粘贴自动脱敏这一目标**。自动模式须验证早期拦截、原生粘贴事件和编辑器
重建等路径；不能仅凭取消默认插入就宣传“官网脚本绝对看不到原文”。网站若另有剪贴板读取权限，
仍可独立读取；本批不新增权限来阻止这一路径，设置明确说明保护范围。

首批检测范围采用可解释的本地规则：邮箱、手机号候选、明确列出的密钥/令牌
格式（`sk-`、GitHub `gh[pousr]_`、Bearer），以及用户指定的正则匹配替换条目。规则清单逐项说明范围；格式命中
可能误报，因此允许人工调整。未知密钥、任意中文人名和地址的完整语义识别
不在首批承诺内，不默认下载大型识别模型。

用户于 2026-10-30 明确将自定义敏感词改为正则条目，以覆盖拼写、分隔符和编号
等变体。每条有匹配表达式、匹配标志和替换文本，支持固定替换、捕获组引用及
空文本删除；界面按条目增删编辑，不能继续只提供精确词列表。每次都对原始文本
匹配，生成一次待确认候选，不把一条的输出继续交给下一条重扫。旧词条转义为
字面表达式，保留旧匹配含义，不能直接当正则解释。实现状态与规则语法、资源上限、
重叠策略和实际验证见[交付计划](../plans/2026-10-30-chatgpt-native-input.md)。

自定义表达式在本机执行。无效、零长度命中、资源超限等属于检查未完成，不得
静默忽略后宣称未命中；密钥锁定遮盖仍优先于所有自定义替换。用户指定的捕获组
可能保留部分原文，审查必须展示最终替换结果，不能把“有正则命中”视为已全部脱敏。
每条采用常见的全局、从左到右不重叠匹配；不会枚举同一条规则的所有重叠出现。
多条规则冲突时保守遮盖整个重叠区间，不能由新增的宽泛规则解除其他规则的保护。
最终所选候选还须检查已知密钥格式；发现替换或拼接产生密钥时阻止插入，并说明如何修正规则。
有命中但最终候选与原文完全相同时（包括取消全部非密钥项或使用 `$&`），
仍需额外勾选确认会将原文交给网站；界面与源端共同执行，不能通过换一个按钮免除确认。
旧词条保留字面匹配含义，升级后的默认替换是固定 `[REDACTED]`，不再保留旧自定义词的身份别名。

密钥与令牌默认删除或不可逆遮盖，不建立可恢复的密钥映射。普通身份信息
可在同一次粘贴中使用稳定占位符；首批不包含回答自动还原，审查结束后释放
原文及临时映射。若后续加入还原，必须另行确定保留期限和会话绑定。

首批自动模式的验收对象是桌面 Chromium 的 `chatgpt.com` 主对话纯文本输入框。
Firefox、其他 AI 官网、附件/图片、拖拽、语音、脚本填入及特殊编辑界面分别
记录为未覆盖，不能由“都是输入框”推定支持。现有 Firefox 页面功能继续沿用。
富文本不能静默降为纯文本；需要降级时先说明并让用户选择。

### 首批使用二：在 ChatGPT 草稿旁直接改写

1. 用户在 ChatGPT 原生输入框写好草稿，点击新增的“改写草稿”入口。
   有选文时处理选文，否则处理当前输入框的纯文本。
2. 入口打开现有功能选择与材料预览，使用已有“改写输入”或用户保存的做法。
   连接、处理要求和实际发送材料可见；用户点击运行才调用所选 AI。
3. 继续使用当前的原文/建议并列比较，用户确认后替换原选区；支持一次撤销。
   等待期间草稿已变、页面已导航或编辑器拒绝写入时，保留当前草稿并提供重试或复制。
4. 改写后的文字留在官网输入框，由用户决定是否发送。不会自动读取整段会话，
   不会把每次改写都作为新的官网聊天消息提交。

这里新增的是就近入口、对原生编辑器的准确识别及可靠回填。模型调用、功能
目录、预览与撤销都复用现有实现。首批不做逐处接受/拒绝的 diff 编辑器，
不新增通用写作服务，也不要求用户更换已有的 Raycast/PopClip 工作方式。

两个新增功能分别开关。本地安全粘贴无需配置 AI 连接；主动改写需要已有可用
连接，未配置时给出设置入口。安全粘贴只覆盖声明的粘贴路径，不因此宣称手工
输入、已有草稿、所有 Box 请求和 API/MCP 请求都已脱敏。主动改写仍遵守现有
材料预览与用户运行规则，不能把原文送给一个“请帮我脱敏”的远端功能冒充本地检查。

### 哪些复用，哪些由本项目补充

完整使用场景会跨越多个职责。MECE 按原子动作的最具体上下文划分；
“在哪调用”“谁执行”“采用何种工具”“先做什么”分别判断，避免把完整产品
硬塞进一个互斥分类。

| 层级与动作依赖 | 承接方式 | 这次具体落点 |
| --- | --- | --- |
| 材料层：只需要明确交出的文本 | 通用写作优先沿用现有 Functions/引擎或用户已有系统工具；本地检测优先复用许可合适的规则/库 | 不重建 Raycast/PopClip；本地规则不经过 AI 引擎 |
| 浏览器层：需要选区、文档与编辑生命周期 | 复用浏览器助手的材料快照、结果预览、过期检查、受控回填与撤销 | 让同一份改写结果能可靠用回当前输入位置 |
| 站点层：需要 ChatGPT 自己的编辑器与页面语义 | 新增薄层官网适配，定位原生输入框、识别重建与导航、放置功能入口 | 自动粘贴拦截与“改写草稿”入口；不另建官网会话数据库 |

现成组合是本提案的最强替代：现有 ChatGPTBox 加系统工具、官网原生能力和
专用扩展。Raycast 与 PopClip 已覆盖不少选文处理和原位改写，不能用“浏览器里
润色”本身证明重复建设的价值。拟新增的价值在于普通粘贴的自动本地策略、
网站明确适配和当前任务中的就近入口；公开资料尚不能证明这些增量优于所有
现成组合，实施验证时需要用同一任务比较操作成本与结果。

若用户已有组合能以相同范围、可靠性和隐私要求完成任务，就允许共存并停用
本项目的对应入口；不要求购买指定桌面软件，不擅自改动其他扩展。
Gateway/MCP 仍是外部调用接口，不作为能力分类的第四层，也不成为官网增强的前置。

### 设置、隐私与失败时的具体行为

`Sites` 中为 ChatGPT 增加相互独立的安全粘贴、改写入口开关，以及适用范围和
当前可用状态。`Functions` 继续管理可复用做法，`Engines` 与现有引擎分区管理
连接。关闭 ChatGPT Web 引擎或本机 gateway 后，本地安全粘贴仍能工作；
官网改写可以使用用户选择的其他已配置连接。两项默认关闭，控件已在
`Sites` 实现；Firefox 没有自动粘贴开关。自定义规则保存于配置并进入完整备份，
与不持久化的本次粘贴原文分开说明。
规则保存以实际存储成功为准，写失败时保留可重试的草稿，不把它显示成生效策略。
另一设置窗口改变规则时保留本窗口未保存草稿并提示冲突；用户明确选择载入已保存规则，
或保留草稿用于下一次覆盖保存。初始读取不能覆盖读取期间已收到的新策略。
初始设置仍在读取或读取失败时，官网增强区显示加载/失败状态并禁止修改，
提供重新加载入口，不能把默认空规则当作已经确认的已保存策略。

安全粘贴拦下的原文、命中明细和临时映射只进入本地检查与扩展自有源审查界面，
不写入官网 DOM（包括注入浮层和 Shadow DOM）、聊天记录、导出、诊断日志或同步。
网站旁的状态提示不包含敏感值。扩展自有源隔离宿主网站，但不等于隔离本扩展
内部全部受信代码或其他高权限软件。

检查中、待确认、已插入、失败、目标已失效与未支持有可区分状态，并提供键盘
可达的下一步。检查或审查未结束时，拒绝新的粘贴并提示先完成或取消当前操作，
不插入新原文、不排队保存第二份材料。切换目标、关闭审查窗、
文档导航、输入框重建或扩展断连会取消待处理项并释放原文。账号切换若不触发
这些边界，尚未建立单独识别保证。服务 worker 重启不恢复审查身份，源操作
仍有五分钟到期上限；不承诺跨重启恢复。应用前重新核对文档与
选区，不覆盖用户后续编辑。处理超时、超长或缺依赖显示具体失败/重试提示，不显示
“未发现敏感信息”。用户仍可取消、重试或明确选择这一次按原样插入；该选择
不能记为检查通过，也不能变成默认失败回退。

检测范围与资源上限由[使用指南](../browser-assistant.md#chatgpt-官网输入增强)列明。
仅接管已识别的主输入框。其他输入框与未知编辑器保留原生粘贴，状态提示不支持，
不能视为受保护；避免把官网搜索、重命名等输入也一起阻止。关闭时不装载早期入口，
启停操作先核对注册或移除效果再发布成功；启动恢复注册失败时，确认清理后撤销
开启状态。若浏览器 API 无法确认状态，明确提示请勿依赖保护并要求重新加载重试，
不能宣称已启用或已成功关闭。开启后刷新页面；已确认关闭的文档不因其他设置
刷新重新接管。已开启文档的配置暂不可读时，主输入框才采取
阻止原文插入、提示稍后重试的策略。手工安全粘贴替代先在
扩展窗口取得原文，适用于不能证明普通粘贴事件保密的环境；它有不同的操作成本。
若自动模式只能在发送前替换、网站已经可能读到原文，就不能按隐私保护验收。

### 交付次序与完成终点

| 次序 | 明确交付什么 | 完成标准或后置原因 |
| --- | --- | --- |
| 第一批：官网输入工作流 | 上述普通粘贴本地脱敏、草稿改写入口、独立设置与失效提示 | 在声明支持的浏览器/输入框中完整走通两条使用路径；只有规则函数或按钮不算完成 |
| 第二批：各自独立评估 | 官网原生消息的实际模型/耗时/思考信息；按次回答还原；确有收益的写作差异交互 | 不作为首批依赖；需要分别核对原生信息来源、映射保留成本和现成工具覆盖 |
| 暂不建设 | Pro 额度估算、用量卡、图片额度面板、WebDAV/多端同步、全局剪贴板、通用写作或 agent 平台 | 不直接完成首批输入任务；另有状态准确性、权限与长期维护成本 |

第一批实施先验证最容易推翻方案的自动粘贴与原生编辑器路径，再接通本地规则、
审查和受控回填；草稿入口复用现有功能链，最后一起核对设置与关闭/降级行为。
ChatGPT-Toolkit 的原生消息标签与绑定经验留给第二批参考，不把其统计和同步
模块一起移入。安全路径的可行性是实现不确定性，不把“已完成调查”写成已交付功能。

验收使用非敏感样例，覆盖正常/命中/误报文本、中文输入法、连续粘贴、编辑器
重建、等待中继续编辑、取消、导航、账号切换、重启与处理器失败。隐私路径
同时观察页面事件、DOM、日志、存储与网络，确认原文没有通过未声明的路径
暴露；改写路径确认只有主动运行才调用已选连接、没有自动发送官网消息。
记录具体浏览器、网站路径、版本、检测语言与未覆盖项，不编造识别率或使用频次。

首批代码已实现，状态和实际证据由[交付计划](../plans/2026-10-30-chatgpt-native-input.md)记录。
隐私方案已通过配置的 `ask_chatgpt` 进行实现前与身份握手审查；完成评价
仍需包含最终代码和观察结果，不能由此前的设计模型比较或当前自审替代。若自动拦截不能达到声明的隐私边界，应报告该项未完成
并修改范围或采用明确的替代，不用手工工具的成功替代自动模式的完成证据。
